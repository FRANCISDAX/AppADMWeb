# AGENTS.md — appadm-web

## What this is

React + TypeScript SPA (point-of-sale / inventory admin) backed by Firebase (Auth + Firestore). No router — navigation is state-driven in `src/App.tsx`. UI language is Spanish.

**Repos relacionados** (los versiona el usuario, **no** este agente): la app móvil **`AppAdm`** (Expo/React Native), el **backend `appadm-sunat`** (FastAPI + `sunat_py`, corre en `192.168.1.7:8000`) y el **puente de Yape `appadm-yape-puente`** (Android/Kotlin: escucha la notificación de Yape y escribe `tblPagosYape`). Un cambio puede tocar los cuatro: si un defecto se arregla acá y **el mismo defecto existe en la RN, se arregla también** y se avisa (no alcanza con arreglar el web).

## Invariantes y trampas (leer antes de tocar código)

Reglas que ya costaron un bug o que salieron de una decisión explícita del usuario. **No "arreglarlas" por iniciativa propia.**

### Caja y arqueo
- **El arqueo cuadra el efectivo, y nada más**: `efectivoEsperado = montoInicial + totalEfectivo − gastosEfectivo − vueltoTransferencia`. Las transferencias **no entran** (ni ahí, ni en `totalNeto = totalVentas − totalGastos`, ni en la diferencia). Cambiar `totalTransferencia` de un turno **no puede** mover el esperado, el contado ni la diferencia: en el arqueo la transferencia es **informativa**.
- 🔑 **Esa fórmula vive en UN solo lugar: `efectivoEsperadoDe()` (`lib/arqueo.ts`).** Estaba escrita a mano en **6** sitios y **dos** de ellos **sin restar `vueltoTransferencia`** (el modal de cierre y `analizarCierre`): el cajero comparaba contra un número distinto al que el sistema guardaba. **No volver a escribirla a mano** (la usan `turnos.ts` ×2, `reportes.ts`, `egresos.ts`, `compras.ts`, `CierreCaja.tsx` y `auditoria-caja.ts`). Verificado: **92/92 turnos cerrados** dan idéntico al `efectivoEsperado` guardado.
- ⚠️ **El consolidado "Caja del día" suma SOLO turnos cerrados.** Un turno abierto tiene esperado pero **todavía no tiene contado**, así que incluirlo inventa una diferencia: con el 16/09 (un cerrado + uno abierto) daba **−11.00** falso. Ahora `montoInicialTotal` / `efectivoEsperadoTotal` / `efectivoContadoTotal` se acumulan solo si `estado === 'cerrado'`, y el rótulo avisa cuántos quedaron abiertos.
- **`tipo` = bolsillo, `medio` = detalle.** Se guarda `{ tipo: 'efectivo' | 'transferencia', medio: 'efectivo' | 'yape' | 'plin' | 'transferencia' | 'tarjeta', monto, operacion? }`. `tipo` es lo que ya entienden el arqueo, los reportes, las anulaciones, el cobro y la RN: **poner `tipo: 'yape'` rompe ~8 lugares en silencio**.
- ⚠️ **`bolsilloDe()` devuelve `'credito'` para `'credito'`, `'mixto'` y cualquier valor desconocido** — **nunca cae a efectivo**. Un medio desconocido que cayera a efectivo **infla el cajón** y produce un faltante fantasma (fue un bug real, ver bloque ·10). Reparto de una venta: **`bolsillosDeVenta()`** (`lib/pagos.ts`) como **regla única**, usada por el alta **y** la anulación.
- **Una venta a crédito no entra a ningún bolsillo** (queda por cobrar); **un cobro de crédito sí**, en el bolsillo del medio con que se cobró.
- **Cada bolsillo tiene dos ejes**: el **total** (plata que entró al cajón/banco: contra eso se concilia) y el **origen** (`lib/arqueo.ts`: ventas del día / cobranza de crédito / notas). Ahí `ventas` es el **residuo** — las partes siempre suman el total guardado, y `consistente: false` avisa si lo derivado no lo explica.
- **Conciliación por billetera (`mediosDelTurno`, `lib/arqueo.ts`)** = lo que el sistema dice que entró por Yape/Plin/tarjeta, para cruzarlo contra la app/banco. Se declara al cerrar (**opcional**, se guarda como `conciliacion` en el turno y en `tblCierresCaja`) y se muestra en el arqueo y en el PDF del cierre. ⚠️ **El `medio` fino existe desde el 16/09/2026**: antes todo cae en **"Transferencia (sin detalle)"** — no inventar un medio. Y una **NC** también cae ahí, porque `notas.ts` guarda el bolsillo del original, no su medio. Verificado: en **49/49** turnos con medios, la suma por medio coincide con el `totalTransferencia` guardado.
- **Conteo ciego** (`config.conteoCiego`, Configuración → Empresa, **apagado por defecto**): al cerrar, el cajero escribe el conteo **sin ver** el "Debería haber"; la diferencia aparece recién en el paso de análisis. Es el control que evita que alguien "cuadre" copiando el esperado.
- **Los documentos de caja van identificados y firmados**: `abrirPDFArqueo`/`abrirPDFCierreCaja` reciben `empresa` (`EmpresaPDF`: nombre, RUC, dirección) e imprimen **dos líneas de firma** (cajero —con quién cerró el turno— y supervisor). ⚠️ Si se agrega un PDF de caja nuevo, **pasarle la empresa y las firmas** (ya están en Configuración → Empresa).
- **`tblTurnos` es registro de caja: no se reescribe.** Para corregir un turno histórico se pide permiso, se toca **solo** el campo necesario (el turno **y** su doc de `tblCierresCaja`), se deja `observaciones` y se registra en `tblAuditLog`.
- ⚠️ **Las fechas de los items del turno se guardan en UTC**; las de turno/reportes son locales. Un cobro de las 21:43 del 14 figura como **15/09 02:43Z**: un turno del 14 puede tener items "del 15" sin que nada esté mal.
- El cajero opera con **su** turno, salvo `verTodo` (supervisor). No se emite comprobante **ni se cobra crédito** con el turno cerrado.

### Fiscal (SUNAT)
- **`Producto.precio` es precio FINAL al público (con IGV incluido)**: no se recarga el 18% al cobrar ni se guarda el precio sin IGV.
- **El comprobante declara lo que se COBRA**: `lib/sunat-importes.ts` reparte el descuento por línea **antes** de despejar el IGV. Al revés, el descuento se aplicaría sobre una base que ya no es la cobrada.
- 🔑 **La BOLETA CONSOLIDADA (consolidación de las NV del día) tiene que declarar el descuento de las NV que agrupa**: `generarConsolidado` (`services/consolidado.ts`) suma los totales (ya netos) y arma las líneas con los items de cada NV **a precio de lista**, así que el descuento va **declarado aparte** (`descuentoTotal` + `descuento_total` = Σ `descuentoDeVenta(nv.venta)`). 📌 **Bug del 18/09/2026**: el consolidador **tiraba el descuento** y unía los items por `id` sin mirar el precio → una NV con promoción, consolidada, salía con las líneas a precio de lista, el **total menor** y **sin ninguna fila de descuento** que lo explicara; y como el XML arma su total con `Σ líneas`, SUNAT habría recibido **más de lo cobrado**. Las reglas viven en **`lib/consolidado.ts`** (`consolidarItems` — la clave de agrupación es **`id|precio|unidad`**: dos NV pueden vender el mismo producto a precios distintos y unirlas dejaría un precio unitario que no explica el subtotal, justo lo que el comprobante declara—, `totalConsolidado`, `descuentoConsolidado`), puras y testeadas. ⚠️ **La RN tiene el mismo defecto** en `helper/ConsolidadoHelper.js`: hay que portarlo cuando se retome la móvil.
- **El IGV solo existe en afectación `'10'`**: `valorUnitarioSunat(precio, afectacion)` divide entre 1.18 **solo** para `'10'`; exonerado `'20'`, inafecto `'30'` y gratuitas van tal cual (dividirlas haría que el comprobante declare **menos** de lo cobrado).
- 🔑 **El receptor de la BOLETA CONSOLIDADA es configurable** (`config.clienteDefaultNombre` / `clienteDefaultDni`, editables en **Configuración → SUNAT → Boleta consolidada**; la regla única son `nombreClienteConsolidado()` y `documentoClienteConsolidado()` en **`lib/consolidado.ts`**, puras y testeadas). Una consolidada agrupa las NV del día: **no hay cliente real** ⇒ va con documento `00000000` y el nombre es un **rótulo** (por defecto `CONSUMIDOR FINAL`; hay negocios que quieren `VENTAS DEL DÍA` o `CLIENTES VARIOS`). 📌 **Estaba a medias**: el consolidador ya leía esos dos campos, pero **no existía dónde configurarlos** (no estaban en `CONFIG_POR_DEFECTO` ni en ninguna pantalla). ⚠️ **Un nombre vacío vuelve al valor por defecto** (nunca se declara un receptor en blanco) y, como ese rótulo **se declara a SUNAT**, cambiarlo es una decisión fiscal. No requiere migración: sin el campo, se usa el respaldo.
- **Los items manuales del PDV** usan `config.tipoAfectacionManual` (default `'20'`) y **debe coincidir con el catálogo**: si no, el comprobante declara más (o menos) de lo cobrado.
- **El backend vive aparte** (`appadm-sunat`): un cambio ahí **no hace efecto hasta reiniciarlo**, y lo despliega el usuario. El SDK `sunat_py` es de PyPI y **no se toca**: el backend parchea el XML por `replace` antes de firmar.
- 🔑 **Todo lo que se manda a la API de SUNAT va con 2 DECIMALES** (`cantidad`, `precio_unitario` y los totales): el backend valida con Pydantic (`app/schemas/invoice.py`) y **rechaza el envío con *"decimal input should have no more that 2 decimal places"***. La regla vive en **`itemsParaSunat()`** (`lib/sunat-importes.ts`, puro y testeado): reparte el descuento y deja el precio unitario en 2 decimales **sin perder el total cobrado** (el residuo del redondeo se repone línea por línea, de la más flexible —cantidad 1— a la menos flexible, en pasos de `cantidad` céntimos); `cantidadSunat()` ajusta la cantidad (una venta por peso con 3 decimales se declara con 2); en las líneas **gravadas** el valor sin IGV (`precio / 1.18`) también se redondea; y **todos los totales** pasan por `redondear2()`. ⚠️ **El backend IGNORA el bloque `totales`**: arma el XML con `cantidad × precio_unitario` de cada línea (`app/services/invoice_service.py`), así que lo que manda es el **precio unitario por línea**. 📌 **Bug del 18/09/2026**: el web mandaba hasta **6** decimales (`DECIMALES_PRECIO`): una línea con descuento daba `1.09 / 2 = 0.545` y el envío se caía. ⚠️ **La RN tiene el mismo defecto** (`AppAdm/services/sunat.js`).
- 🔑 **Los correlativos tienen DOS espacios y viven en `tblContadores`**: `notaVenta_{serie}` para **notas de venta** y `sunat_{serie}` para boletas, facturas y NC/ND. La clave se arma **siempre** con **`claveContador(tipoDoc, serie)`** y el campo es **`CAMPO_CONTADOR` = `ultimoCorrelativo`** (ambos en `lib/contadores.ts`, puro y testeado); se **siembra desde el máximo ya emitido** cuando el contador no existe. ⚠️ **Regla que ya se rompió**: el flujo de ventas pendientes usaba `sunat_{serie}` para todo y escribía el campo `contador` → nació un contador paralelo **`sunat_NV01` que arrancaba en 1** mientras las NV iban por `notaVenta_NV01 = 173`, y la siguiente NV pendiente habría **repetido un número ya emitido**. Nunca escribir la clave ni el campo a mano.

### Envío automático a SUNAT (web)
- 🔑 **Una regla (`lib/sunat-auto.ts`, puro y testeado) y un solo camino de envío**: `services/sunat-auto.ts` reclama y manda con `enviarDocumentoASunat`/`enviarNotaASunat` (los del botón manual); `use-sunat-auto.ts` (montado en el `Shell`) lo corre al abrir, cada `sunatAutoIntervaloMinutos` y al volver el internet. **Plazo único y configurable: 3 días** (`config.sunatAutoDiasVencimiento`), medido en **día local** (la factura vence a los 3 y la boleta a los 7 ⇒ se usa el más estricto).
- ⚠️ **Nunca se manda solo**: NV y pedidos, lo `aceptado`, lo `rechazado`, lo `anulado` ni **lo vencido**; el **botón manual manda todo eso** y sigue igual con el automático apagado (`respetarInterruptor: false` en «Enviar pendientes ahora»). Una nota **espera a que su comprobante esté `aceptado`** (fail-open si no lo encuentra).
- 🔑 **Reclamo transaccional** (`reclamarDocumentoSunat`): sin él **dos pestañas mandan el mismo comprobante**; un `enviando` colgado se recupera a los 5 min y un duplicado no daña (**1033** = aceptado). La consulta es **una igualdad sobre `sunat.estado`** (`pendiente`/`error`/`enviando`/**`rechazado`** ⇒ **sin índice compuesto**): `rechazado` está **solo para la alerta** (📌 sin él no se disparaba nunca).
- 🔑 **El interruptor se lee del SERVIDOR** (`getDocFromServer`: con la caché llega viejo y una pasada podía mandar **con el automático apagado**). Alertas: `sunat-pendiente` y `sunat-rechazado`. ⚠️ **Manda el NAVEGADOR**: solo cubre los días en que alguien abre el app y la página tiene que **alcanzar la API** (el CSP de `firebase.json` no permite una IP de la red local, y desde `https` un `http://…` sería contenido mixto).

### Pedidos (venta enviada a caja) y stock
- **Un pedido no es un comprobante**: `tipo: 'PENDIENTE'`, `serie: ''`, `numero: 0`, sin bloque `sunat`, sin forma de pago, y su código `PED-000123` sale del contador `pedido` (`CLAVE_PEDIDO` + `codigoPedido`, `lib/contadores.ts`). **La serie y el correlativo se asignan una sola vez, al cobrar** (`cobrarVentaPendiente`, con `claveContador(tipoFinal, serieDestino)`); eliminar un pedido **no deja huecos**. No volver a numerar en el alta.
- 🔑 **El pedido NO toca el stock: el inventario se descuenta recién al cobrar, en UN solo lugar** (`cobrarVentaPendiente`). Decisión explícita del usuario (17/09): *"un pedido es un ticket en espera, no una reserva"*. Antes reservaba stock con movimientos `venta_pendiente` y había que reponerlos al eliminar; eso creaba **dos caminos de escritura de stock** (alta y cobro) y dejaba stock retenido si el pedido quedaba colgado. **No reintroducir la reserva sin hablarlo**: si algún día se quiere apartar producto (seña, cliente que vuelve), va como **capa explícita y visible** (campo `reservado` mostrado en el catálogo), no como descuento silencioso.
- **Eliminar un pedido = marcarlo `cancelado`** (`cancelarVentaPendiente`, con motivo obligatorio): **una sola escritura** — no lee ni escribe `tblProductos` ni crea movimientos, porque no hay nada que deshacer. Se registra en `tblAuditLog` (`accion: 'eliminar_venta_pendiente'`). ⚠️ **No es un borrado físico**: el documento queda en `tblDocumentos` con `estado: 'cancelado'`, el motivo y quién lo eliminó — sirve para rastrear por qué un pedido no llegó a comprobante. Desaparece de la lista de pendientes (`obtenerVentasPendientes` filtra `estado == 'pendiente'`) y **de todos los reportes** (filtran `tipoDoc` contra `NV/BOLETA/FACTURA/NC/ND`).
- **Los pedidos los ve el cajero en el PDV**, no en una pantalla aparte: `PanelVentasPendientes` se monta arriba del carrito y solo si tiene `verVentasPendientes`. ⚠️ **La lista NUNCA debe depender de la caja para mostrarse**: `obtenerVentasPendientes()` trae **todos** los pendientes y el reparto lo decide **`repartirPedidos()`** (`lib/pedidos.ts`), no la consulta. Filtrar en Firestore (o esconder el panel con `if (!cajaId) return null`) fue el bug real del 17/09: el vendedor tenía `caja_principal`, **los cajeros no tenían caja**, y el pedido `PED-000001` era **imposible de cobrar** porque la lista salía vacía y el panel escondido. Un pedido que no se ve es una venta perdida: **ante la duda, mostrar**.
- ⚠️ **El cobro de un pedido usa las series de la caja del CAJERO** (`serieBoleta`/`serieFactura`/`serie_prefijo` de `usePermisos()`, con la config de la empresa como respaldo) igual que el PDV: si no, un cajero de la caja 2 emitiría con la serie de la caja 1.
- **Cajas = puntos de emisión** (`services/cajas.ts`): nombre + **8 series** (Boleta, Factura, NV, NC, ND, NCB, NDB). Se crean en **Configuración → Cajas** y se asignan al usuario en **Usuarios → Editar → Caja**. ⚠️ **Quien la necesita es el CAJERO** (es quien emite: define con qué serie sale el comprobante); el **vendedor no** — su caja solo **dirige** el pedido. Si un usuario no tiene caja, se usan las series de la configuración de la empresa (funciona, pero deja de ser explícito).
- 🔑 **Caída de una caja con pedidos abiertos (decisión del usuario, 17/09)**: el `cajaId` de un pedido es **de ruteo** y **nadie más lo lee** (las series las pone la caja que **cobra**), así que conviven dos mecanismos: **(A) transferir** los pedidos abiertos (**Configuración → Cajas → Transferir pedidos**, `moverPedidosDeCaja()`: `writeBatch` + `tblAuditLog`, devuelve cuántos movió) y **(B) rescate**: el panel muestra los de **otra** caja en un bloque aparte y los deja cobrar con confirmación (*"se va a emitir con la serie de tu caja"*). Con (A) queda el orden; con (B) no se pierde una venta si nadie transfirió. El reparto es **`repartirPedidos()`** (`lib/pedidos.ts`, puro y testeado): sin caja se ve todo, con caja los propios + los sin caja, y los ajenos van a `otrasCajas` (nunca se ocultan). El documento cobrado queda con **la caja que lo emitió**.
- 🔑 **Modo pedido: el cobro ocurre en el CARRITO, no en la tarjeta** (decisión del usuario, 17/09). `Cobrar pedido` llama a `onCobrarPedido` y el PDV guarda `pedidoActivo` (`lib/pedidos.ts` → `pedidoParaCarrito()`): el carrito muestra **sus** items en solo lectura (franja ámbar) y el cajero elige **comprobante + forma de pago** con la UI de abajo; el botón pasa a **`Cobrar pedido S/ …`** → `cobrarVentaPendiente`. 🔑 **`total` es el del pedido cuando hay pedido activo** (`const total = pedidoActivo ? pedidoActivo.total : totalCarrito`), así el resumen de pagos y las validaciones no pueden contradecirse: **es el monto COTIZADO por el vendedor y no se recalcula** con las promos del día. En modo pedido se ocultan **envío, descuentos, cliente, crédito** y las acciones del carrito. ⚠️ **No volver a poner un cobro embebido en la tarjeta**: tenía su propia copia de comprobante, formas de pago y validaciones — dos lugares y dos reglas para lo mismo.
- 🔑 **El crédito se maneja directamente en caja (decisión del usuario, 17/09)**: un pedido del vendedor se cobra **siempre al contado** y por eso **en modo pedido no se ofrece "Crédito"**. Si el cliente quiere fiado, el **cajero** arma la venta como cualquier otra y la cobra a crédito con la validación de saldo (`lib/credito.ts`). El vendedor tampoco elige forma de pago al enviar, así que **un pedido nunca nace con intención de crédito**. ⚠️ Si algún día se quisiera permitir, hay que resolver antes qué pasa con el saldo: `calcularSaldoCredito` lee `venta.tipoPago === 'credito'` y `cobrado`, y `cobrarVentaPendiente` no escribe `cobrado`.
- **Al cobrar, si el stock ya no alcanza, el cobro falla con un mensaje claro** (*"El stock de X se agotó mientras el pedido esperaba en caja"*): es el costo de no reservar (otro vendedor pudo vender esas unidades) y el cajero tiene que enterarse antes de cobrar, no después con el inventario mintiendo.
- **Dos personas en una venta = una regla, `lib/personal.ts`** (`personalDeVenta`, `lineasPersonal`, `textoPersonal`): **con vendedor y cajero distintos salen los dos; si trabajó una sola persona, sale una sola vez**. Se usan `venta.vendedor` (quien armó el pedido) y `venta.cajero` (quien cobró), con `doc.vendedorNombre`/`doc.cajero` de respaldo. ⚠️ `registrarVenta` escribe el **mismo usuario** en `cajero` y `vendedorNombre`, así que la regla **colapsa el nombre repetido** (si no, el ticket lo diría dos veces). ⚠️ **`venta.cajero` de un pedido NO es el vendedor** (era el bug: al mandar a caja se escribía el vendedor y el comprobante lo imprimía como si hubiera cobrado él); al cobrar se guardan los dos y se imprime (`Vendedor: Ana · Cajero: Luis`), y en el arqueo por comprobante como `· Vend: Ana` (solo si no es el cajero del turno).
- ⚠️ **Los movimientos de stock siguen el formato del kardex** (`services/kardex.ts`): `tipoMovimiento`, `cantidad` **positiva** y el signo lo decide `esEntrada()`; además `stockAnterior`/`stockNuevo`/`fecha`. Un `tipo` suelto o una `cantidad` negativa no se leen (quedan invisibles en el kardex). El cobro de un pedido escribe un movimiento `venta` igual que `registrarVenta` (con `vecesVendido: increment(1)`).
- 🔑 **Un pedido tiene que declarar el DESCUENTO igual que una venta directa**: `crearVentaPendiente` guarda **`descuentoTotal`** (camelCase: el que leen `lib/pdf.ts` y `lib/sunat.ts`) **y** `descuento_total` (nombre viejo). 📌 **Bug del 18/09/2026**: el pedido guardaba **solo** `descuento_total`, así que al cobrarlo el comprobante **no veía descuento**: sumaba las líneas a **precio de lista** y declaraba el total ya descontado (2 huevos con promo «2 o más a S/ 0.50» + 2 galletas: líneas 2.20, `TOTAL IMPORTE` 2.00) **sin ninguna fila de descuento** que lo explicara — y el XML habría declarado 2.20. **La lectura es una sola regla: `descuentoDeVenta(venta)`** (`lib/sunat-importes.ts`, pura y testeada: camelCase con respaldo en snake_case) y la usan el PDF, el XML de SUNAT y el carrito del cajero (`pedidoParaCarrito().descuento`, que se muestra en la franja ámbar del modo pedido para que el cajero vea el descuento del vendedor). ⚠️ Los **precios de las líneas siguen siendo los de lista**: lo que se declara es el total con la fila `Descuento` (modelo SUNAT), no un precio unitario ya rebajado.
- 🔁 **Un pedido idéntico no se crea dos veces**: si el mismo vendedor manda la misma venta y ese pedido **sigue pendiente dentro de los 15 minutos** (`VENTANA_DUPLICADO_MINUTOS`), `crearVentaPendiente` **rechaza el alta** y devuelve el código del que ya existe (`{ duplicado: true, codigoPedido }`); el PDV entonces pide confirmación (*"¿Enviar otro igual?"*) para el caso legítimo —otra venta con los mismos productos—, y con `permitirDuplicado: true` el documento queda marcado `duplicadoConfirmado: true`. 📌 **Caso real (18/09/2026)**: un reenvío creaba `PED-000123` **y** `PED-000124`; el cajero cobraba uno y el otro quedaba colgado **para siempre** en su lista, aparentando *"un pedido ya procesado que sigue apareciendo"* (y el stock se descontaba una sola vez, así que el sobrante no se notaba por inventario). Las reglas viven en **`lib/pedidos.ts`** (`huellaPedido()`: vendedor + total + líneas ordenadas, **sin fecha** —para reconocer el reenvío— y sin cliente; y `pedidoDuplicado()`, que también recalcula la huella de los pedidos viejos que no la tienen guardada), puras y testeadas. ⚠️ La comprobación es **fail-open a propósito**: si la consulta de pendientes falla, el pedido se crea igual — es una ayuda contra el error humano, no un candado que pueda bloquear una venta.
- 🧭 **Listado de pedidos y quién ve qué (decisión del usuario, 18/09/2026)**: `Reportes → Pedidos` muestra los pedidos del mes con su ciclo completo —*En caja*, *Cobrado* (con **el comprobante emitido** y quién lo cobró) y *Eliminado* (con **el motivo**)— leyendo `obtenerPedidosDelMes()` (`services/ventas.ts`), que usa **una sola igualdad (`anioMes`) y filtra en JavaScript ⇒ sin índice compuesto**. Un pedido se reconoce **en cualquier estado** con **`esPedido()`** (`lib/pedidos.ts`): `tipoDoc === 'PENDIENTE'` mientras espera, y el campo **`pedido`** (el `PED-…` que `cobrarVentaPendiente` conserva al cobrar) cuando ya tiene comprobante — ⚠️ **sin esa segunda marca, un pedido cobrado sería indistinguible de una venta directa del cajero**. 🔑 **Visibilidad: `pedidosVisiblesPara()`** — `verTodo` (admin/supervisor) ve **todos**; el **vendedor** solo **los suyos** (`vendedorId`) y el **cajero** los que **cobró** (`cajeroId`) más los que haya armado. La regla vive en `lib/pedidos.ts` (pura y testeada) para que la pantalla no la reinterprete. Las tres acciones del ciclo quedan además en `tblAuditLog` con rótulo propio (*Enviar pedido a caja*, *Cobrar pedido*, *Eliminar pedido*) bajo el módulo **Pedidos**.

### Inventario valorizado (costo promedio ponderado)
- 🔑 **El costo con el que se valoriza el stock es UNO solo: `costoDeProducto()` (`lib/valorizacion.ts`)** — el **promedio ponderado móvil** (`producto.costoPromedio`, guardado con **4 decimales**) y, mientras el producto no tenga uno, el **último costo** (`ultimoCostoDeProducto()`: `precioCompra` y, si está vacío o en **0**, el campo viejo `costo`) **como respaldo**. Lo usan el kardex (columnas *Costo unit.* y *Valor*), el reporte **Valorización** de Inventario, los **reportes de inventario** (`lib/inventario-reportes.ts`: stock general, mayor inversión, por categoría, general y utilidad), el **margen** de `services/analisis.ts` y el aviso **BAJO COSTO** del PDV. **No volver a escribir `stock × precioCompra` ni leer `precioCompra` a mano para plata.**
- 📌 **Bug del 19/09/2026 (el costo partido en dos)**: la valorización ya usaba el promedio, pero Análisis (margen bruto y utilidad por producto) y los reportes de utilidad seguían leyendo `precioCompra` → **dos costos distintos del mismo producto en dos pantallas de la app**, y el equivocado era el que se mira para decidir precios. Y **ninguna compra escribía `precioCompra`** (solo el formulario manual), así que ese campo quedaba viejo: medido en producción, **8 de 36** productos no coincidían con la última compra del kardex. **Ahora `registrarCompra` escribe `precioCompra` = costo por unidad base** (`costoUnitario ÷ factor`) y registra el cambio en `tblHistorialPrecios` (después de la transacción, sin `await`). ⚠️ Un ítem con costo 0 (bonificación) **no** lo pisa.
- ⚠️ **Un producto con stock y sin ningún costo vale S/ 0** en la valorización **y da 100% de margen** en el reporte de utilidad: no se distingue «no hay dato» de «costo cero». Es una limitación conocida (el Inventario avisa *"N sin costo (valen S/ 0)"* y el Excel lo rotula *Sin costo (vale 0)*) y está **fijada por un test** en `lib/inventario-reportes.test.ts` para que no cambie sin querer.
- 🔑 **Entrada vs salida (la regla del método)**: una **entrada con costo** (compra) mueve el promedio —`(stockAntes × promedio + cantidad × costo) ÷ stockFinal`—; una **salida** (venta, ajuste negativo) se valoriza **al promedio vigente y NO lo mueve** —la mercadería que sale no arrastra el precio de la última compra, que es la gracia del PPP—; una **entrada SIN costo** (devolución, anulación, ajuste positivo, que no piden costo) se valoriza **al promedio vigente** y tampoco lo mueve: **tratar el costo faltante como 0 hundiría el promedio** y valorizaría el inventario de menos; y con **stock previo ≤ 0** el promedio pasa a ser el costo de la entrada (no hay nada que ponderar y dividir por un stock negativo no tiene sentido).
- 📌 **El promedio se guarda con 4 decimales** (`DECIMALES_COSTO`) y los **valores** con 2: redondear el promedio en cada paso **acumula error**, pero la plata va a céntimos. ⚠️ **La valorización se escribe en los 7 caminos que tocan stock** (compra `compras.ts`, nota de crédito, venta `registrarVenta`, anulación de NV, cobro de pedido `cobrarVentaPendiente`, ajuste y toma física de `Inventario.tsx`) llamando a **`valorizacionDeMovimiento()`** (`services/kardex.ts`, que devuelve `camposProducto` + `camposMovimiento`): **un camino nuevo de stock que no la llame deja el kardex sin costo y el promedio viejo**. El cobro de un pedido lee el `costoPrevio` de cada producto **dentro de la transacción** antes de escribir (el promedio previo no está en el carrito).
- ⚠️ **Los movimientos anteriores a la función no tienen valorización y muestran `s/d`** — no se inventa un costo que nunca se registró. Los productos que no tuvieron una entrada desde entonces se valorizan con el último costo: la columna **Origen del costo** del Excel y el contador **"N con último costo"** del Inventario lo dicen explícitamente (y la primera compra los pasa a promedio). Matemáticamente el respaldo y sembrar el promedio dan lo mismo, así que **no hace falta ninguna migración** de `tblProductos`.

### Comprobantes: dos formatos, un solo cálculo
- 🔑 **El comprobante tiene DOS formatos y ninguna regla duplicada**: el **ticket de 72 mm** para la ticketera (`construirHTMLComprobante` + `abrirPDFComprobante`, `lib/pdf.ts`) y el **A4** para correo/WhatsApp (`lib/comprobante-a4.ts`). Los números salen **siempre** de **`lib/comprobante-comun.ts`** (puro y testeado) y **la ticketera no se toca** al agregar algo al A4: un test-guarda lee `lib/pdf.ts` y falla si cambia el `@page` de 72 mm o si `calcularTotales` se duplica ahí. ⚠️ jsPDF (A4) usa WinAnsi: **sin emojis ni comillas tipográficas** (todo pasa por `limpiarTextoA4()`), y **ningún dato de la tabla se dibuja sin medir el ancho de su columna**. El porqué y los bugs del A4, en el historial.

### PDV: el catálogo se dibuja por páginas
- 🔑 **El catálogo del PDV NO se pinta entero: se dibuja de a `PAGE_CATALOGO` (60) tarjetas** (`Pdv.tsx`: `visibles` + `paginados = lista.slice(0, visibles)`, `InfiniteScroll` + botón *Ver más* + contador *«Mostrando X de Y»*). Medido con **2.000 SKU**: **1.384 nodos** en el DOM contra **32.415** sin paginar, y una tecla de búsqueda en el peor caso pasó de **211-216 ms a 23-46 ms**. ⚠️ **Lo que se pagina es el DIBUJO, no la consulta**: `useProductos()` sigue trayendo el catálogo completo (onSnapshot) y el filtro sigue siendo en memoria, porque **buscar tiene que encontrar cualquier producto, no solo los de la primera página** (verificado: buscar `1999` —el SKU 1.999, que está en la última página— lo encuentra). No cambiar la suscripción por un `limit()`/paginación de Firestore: rompería la búsqueda y el stock en vivo.
- ⚠️ **El reset de la página va en el EVENTO, no en un efecto**: el `onChange` del buscador y los chips de categoría (`filtrarCategoria`) hacen `setVisibles(PAGE_CATALOGO)`. Sincronizarlo con un `useEffect` es justo lo que sube el baseline de lint (80 warnings).
- 📌 **Medido el 21/09/2026 (emulador + build de producción + Chrome headless, 2.000 productos)**: el catálogo completo llega en **6,2-6,6 s** y el heap baja a **11-29 MB** (antes 41-43 MB): **el costo de render dejó de depender del tamaño del catálogo**. En el build de **desarrollo** los mismos números son ~2× peores, así que **medir siempre contra el build de producción**.

El **descuento manual** (global S/ o % que carga una persona en el PDV) es una **decisión de mostrador** y es lo único que se controla.

Un descuento **en soles** se mide como porcentaje del subtotal, así el tope es una sola unidad de medida. ⚠️ **No aplica a las promociones automáticas** ni a `registrarVenta` (para no bloquear al cajero en un caso autorizado).

### Afectación (IGV) — leer antes de tocar cualquier flujo de venta
- 🔑 **La afectación es de CADA PRODUCTO** (`Producto.tipoAfectacion`): manda por encima de cualquier configuración. `afectacionDe(item, { regionExonerada })` (`lib/sunat-importes.ts`, puro y testeado) es la **regla única**: si el item trae la suya, esa; si no, el default del negocio (`config.regionExonerada ? '20' : '10'`). **`config.regionExonerada` NO es un override** — es solo el default de lo que no trae dato (antes era **decorativa**: se mostraba en Configuración y no se usaba en ningún cálculo).
- 🔑 **Los items de un DOCUMENTO llevan otra forma que los del carrito**: el carrito usa `quantity` + `precioVenta` por presentación; el documento usa `cantidad`/`cantidadEnUnidadBase` en **unidades base**, `precioVenta` por **unidad base**, `subtotal`, `unidad`, `categoria` y **`tipoAfectacion`**. 📌 **El bug del 18/09/2026**: `enviarACaja` (pedido) mandaba el formato del carrito, así que los pedidos se guardaban **sin `tipoAfectacion`** → al cobrarlos, `it.tipoAfectacion || '10'` los declaraba **GRAVADOS** y un producto exonerado (`'20'`) salía con **Op. Gravadas + I.G.V. 18%** en el comprobante. Con una venta por presentación (factor > 1) el `subtotal` además habría salido inflado por el factor. **Al agregar un flujo nuevo de venta, copiar el formato de `registrarVenta`**, no el del carrito.
- **Los items de "Embalaje y Otros"** (sin producto en el catálogo) llevan su **propia `afectacion`**: arranca con `config.tipoAfectacionManual` y el cajero la cambia por item con el selector del carrito (catálogo `TIPO_AFECTACION`). Viaja igual en la venta directa y en el pedido; `VentaPausada` la guarda para no perderla al pausar/recuperar.
- **Revisar la afectación con los ojos en el PDF**: si un comprobante muestra filas *Op. Gravadas / I.G.V.*, hay al menos un item declarado `'10'`. En una región exonerada eso es un error, no una cuestión de criterio.

### Firestore
- **Igualdad + rango/orderBy ⇒ índice compuesto** declarado en `firestore.indexes.json` y desplegado con `npx firebase deploy --only firestore:indexes`. ⚠️ **Nunca `firebase deploy --force`** (borra índices que no estén declarados ahí).
- 🔑 **`undefined` NO es un valor válido: Firestore lo RECHAZA al escribir** (*"Function transaction.set() called with invalid data. Unsupported field value: undefined"*) y **TypeScript no avisa** (un campo opcional `string | undefined` compila perfecto). Fue un bug real: **enviar una venta a caja fallaba siempre** porque el payload llevaba `descuentoGlobalTipo: undefined` y `envio: undefined`, y el `tsc` en verde no dijo nada (0 pedidos en producción: nunca había funcionado). **Reglas**: (a) los opcionales que pueden faltar van con **spread condicional** (`...(x ? { campo: x } : {})`) o en **`null`** (`?? null`); (b) **en el borde de escritura**, envolver el payload en **`limpiarUndefined()`** (`lib/limpio.ts`, puro y testeado) — es la red de seguridad: borra los `undefined` en profundidad, descarta los sueltos dentro de arrays y **respeta `null`, `Date`, `Timestamp`, `deleteField()` e `increment()`** (son instancias de clase). Ya se usa en `ventas.ts` (alta, pedido, cobro, anulación), en el guardado de productos de `Inventario.tsx` y en **`services/sunat.ts`** — donde la respuesta del CDR **no siempre trae** `cdr_code`/`cdr_desc`/`hash` y el `updateDoc` del bloque `sunat` fallaba con ese error **aunque SUNAT ya hubiera aceptado el comprobante** (el usuario veía el texto de Firestore y no el resultado del envío); los campos del CDR se normalizan en `datosCdr()` (`?? null`) **y** el payload pasa por `limpiarUndefined()`, y el `actualizar()` del `catch` va en su propio `try` para que un fallo al guardar el estado de error no tape el error real. Para diagnosticar antes de escribir: `rutaConUndefined(payload)` devuelve la ruta del campo culpable.
- `orderBy` **descarta** los documentos a los que les falta el campo: si puede faltar, ordenar en JS.
- **Borrados y actualizaciones masivas, por lotes** (`writeBatch`, 500) devolviendo **lo que realmente se hizo** (nunca 0 por un fallo parcial).
- Nunca `undefined` como valor de campo (spread condicional) ni `!` en lecturas.
- 🔑 **Toda transacción va por `ejecutarTransaccion()` (`services/transacciones.ts`), nunca por `runTransaction` del SDK**: el envoltorio **reintenta** la contención entre cajas (lock timeout, y el `failed-precondition` de *«stored version does not match»*) y, si igual falla, la cambia por *«El sistema está ocupado… Reintenta en un momento — no se registró nada»*. Qué es transitorio lo decide **`lib/reintentos.ts`** (puro y testeado), y ⚠️ **`failed-precondition` es ambiguo**: el de *«requires an index»* **no** se reintenta (bloque ·5). 🛡️ Dos tests-guarda fallan si un servicio usa `runTransaction` directo o si el envoltorio deja de traducir el error.
- **Diagnóstico contra producción**: **solo lectura** con la service account (`firebase-admin` instalado en una carpeta temporal **fuera** de los repos, y borrada al terminar). Los `uid` tienen 28 caracteres: no truncarlos.

### Sesión y sin conexión (offline)
- 🔑 **El cierre de sesión por inactividad (15 min, `App.tsx`) NO corre sin conexión** (decisión del usuario, 21/09/2026). Sin internet, el login de Firebase **no se puede hacer**, así que un logout durante un corte dejaba al local **afuera hasta que volviera la red** (un corte de 20 min se volvía "cerrado hasta que vuelva el internet"). Offline el temporizador se **cancela** y al volver la conexión se rearma con 15 min nuevos (`online` está en las dependencias del efecto). ⚠️ **Consecuencia aceptada**: durante un corte la pantalla no se bloquea sola — lo expuesto es ver catálogo y precios, porque **cobrar y emitir igual requieren conexión**. 🛡️ Está fijado por un test-guarda (`lib/sesion-offline.test.ts`, que lee `App.tsx`): si alguien saca la condición, el test falla.
- **Qué funciona sin internet**: la app **abre sin pedir login** (la sesión vive en el perfil, `browserLocalPersistence`) y deja **consultar** catálogo/clientes **desde la caché**; **no**: entrar desde cero, volver tras un logout, cobrar, emitir a SUNAT. ⚠️ **Nunca borrar el perfil del navegador de una caja** ni usar incógnito.
- 🆘 **Contingencia si se cae el internet del local**: el **celular con datos móviles** sí tiene internet (otra conexión) ⇒ (a) **compartir hotspot** y la PC de caja vuelve a operar normal; (b) o **vender desde el celular** (PWA), que **necesita su cuenta** (la sesión es única) y ticketera de red/Bluetooth. ⚠️ El celular en el Wi‑Fi del local **no** ayuda si ese Wi‑Fi es el que se cortó.

Un aviso real significa «el negocio recibió plata», no «alguien apretó un botón». El contrato del documento (qué campos y de qué tipo) está en la cabecera de **`services/yape.ts`**; ⚠️ `fecha` tiene que ser un **Timestamp de Firestore** (la consulta filtra por rango; un string se tolera al leer pero no lo encuentra la query).
- 🔑 **El ciclo de vida vive en `lib/yape.ts`** (puro y testeado: situación del aviso, lista visible, aplicación a la venta con su tope, resumen y cruce del turno) y **la transacción en `services/yape.ts`** (`reservarPagoYape` → `confirmarPagoYapeEnVenta` → `soltarPagoYape`, + `ignorarPagoYape` y `anularPagoYapeDeVenta`). **No agregar un segundo camino.** El **vencimiento es derivado** (no se guarda) y una **reserva vencida vuelve a estar disponible**: un navegador que se cierra a mitad del cobro no deja el aviso tomado.
- 🔑 **Por qué hay una RESERVA y no solo un candado al final**: el aviso se toma **antes** de cobrar. Si el único control fuera marcarlo `usado` tras guardar la venta, dos cajas aplicarían el mismo yape y la segunda se enteraría **después de haber cobrado**. La reserva es transaccional y **cross-caja** (verificado: la caja 2 ve *«en uso por Ana Cajera»* y no tiene el botón habilitado).
- ⚠️ **Un aviso dice un monto, NO una venta**: el monto que coincide con el total solo se **destaca** (ayuda visual, no una regla) y el cruce real es **al cerrar el turno**: `CierreCaja` (con `pagosYape`, que trae `Turnos.tsx` vía `obtenerPagosYapeDelTurno`) lista los avisos confirmados y **avisa si hubo cobros por Yape y ningún aviso**. ⚠️ Ese prop es `PagoYape[] | null` (**`null` = todavía no llegaron**, `[]` = llegaron y no hay ninguno). **No bloquea el cierre: informa.**
- 🔑 **Al confirmar se guarda el ID DEL DOCUMENTO, no `ventaId`**: `ventaId` es un id interno (`V-…`) que no sirve para encontrar la venta; el documento es `2026-9_BOLETA-B001-000001` (por eso `registrarVenta` devuelve **`documentoId`**). De eso depende que **anular la venta marque el aviso `anulado`** (la plata volvió al cliente), enganchado en `anularNotaVenta` y best-effort — **anular no puede fallar por esto**. ⚠️ **Una NC de una boleta NO está cubierta**.
- ⚠️ **Un estado que la app no entiende no se muestra ni se puede usar**: el panel lo dice (*«N aviso(s) con un estado que el sistema no reconoce»*), para que un puente mal escrito se note en vez de ofrecer avisos dudosos.
- ⚠️ **`firestore.rules` NO se tocó, a propósito**: permite `read, write` a todo autenticado y basta que **una** regla permita, así que un bloque restrictivo para `tblPagosYape` sería **decorativo**. Endurecerlo exige ruleset por colección + cuenta dedicada del puente.
- 🔑 **Con varias cajas, el panel ayuda a no elegir a ciegas** (22/09/2026): la plata entra a **UNA** cuenta Yape, el aviso **no dice de qué caja es** y todos ven la misma lista ⇒ cada aviso muestra **hora con segundos** + **«hace N s»** + pagador + N° de operación; se **avisa** si hay dos del mismo monto (`avisosDelMismoMonto`) y uno que no coincide con el total **pide confirmación** (`confirmarAntesDeAplicar`) — ⚠️ **no es un candado**: el control real es el **cruce del cierre**. 🔑 Muestra el **`codigoSeguridad`** (*«el cód. de seguridad es: 159»*), que es lo único que distingue dos avisos del mismo monto (⚠️ **no es la identidad** ni una prueba: puede repetirse) y **es la referencia del pago** que se guarda, rotulada **`Ref:`** en ticket, A4, arqueo y turnos. 🛡️ `lib/referencia-pago.test.ts`.
- 🔑 **Los avisos anteriores se ven en `Reportes → Yape`** (22/09/2026): el panel del PDV lee **solo los del día** y los confirmados de un turno **solo al cerrarlo**, así que al día siguiente un yapeo era **invisible desde la app**. El historial lee **un rango de fechas** (una sola consulta de un campo ⇒ **sin índice compuesto**) y muestra la **situación derivada** de cada aviso, quién lo usó y en qué comprobante, los **sin usar** y los de **PRUEBA** —marcados, y **no suman**—; el filtro por situación y el buscador van **en memoria** (`filtrarAvisosYape`). 🛡️ Guarda: `lib/yape-historial.test.ts`.
- 🔑 **El latido del puente se ve en el PDV y en Configuración → Yape** (22/09/2026): el celular escribe `tblPuenteYape/estado` **cada 5 min** (y con cada aviso) y el web lo lee **en vivo**. 🔑 **Por qué**: un panel vacío significa «no yapeó nadie» **solo si el puente late**; con el puente caído el panel también está vacío pero **la plata entró**, y antes eso se descubría recién al cerrar el turno. La regla es única, `estadoDelPuente` (`lib/puente.ts`): **activo** < 12 min, **demorado** 12-30, **caído** ≥ 30 (dos ciclos de gracia) y **`sin-datos` NO es «caído»** (nunca escribió). ⚠️ **Vive en la pantalla del PDV, no dentro del panel de avisos** (el panel se oculta cuando no hay avisos, que es justo el caso que importa). ⚠️ **No recupera** lo que el celular nunca leyó ni reemplaza el **cruce del cierre**. 🛡️ `lib/puente.test.ts`.
- 🔑 **El puente es un repo aparte (`appadm-yape-puente`, Android/Kotlin, lo instala el usuario en el celular del negocio)**: usa **su propia cuenta** (no la de una persona: así el rastro no se mezcla y, si se filtran las credenciales del celular, el daño queda acotado), escribe el aviso con **id de documento determinista** —`op_<nroOperacion>` o `nd_<postTime>`— para que una notificación repetida **no cree dos avisos**, y deja el **latido** de arriba. ⚠️ **v1.4: un aviso leído que no se pudo escribir queda EN COLA en el celular** y se reintenta solo (red/heartbeat); si sale tarde va con su **hora original** ⇒ aterriza **vencido**, nunca como plata de ahora.

### Alertas proactivas (`lib/alertas.ts`, **solo web**)
- 🔑 **Una regla, una implementación** (24/09/2026): `evaluarAlertas()` (puro y testeado) corre las reglas —puente de Yape caído/sin datos, turno de otro día sin cerrar, stock agotado (crítico) / bajo el mínimo (aviso), avisos de Yape sin usar o con estado raro, diferencia de caja, anulaciones del día y descuentos **sobre el bruto**— las ordena por severidad y **las pantallas solo dibujan eso**; `services/alertas.ts` **solo lee** lo que ya leía otra pantalla. ⚠️ **Una alerta INFORMA, no bloquea** (ni cobrar, ni cerrar, ni vender) y **`0` = regla apagada** (una config sin los campos nuevos evalúa igual las útiles).
- ⚠️ **No gritar de más**: un turno abierto **normal** es información (quién tiene la caja), no una alarma, y un aviso de Yape sin usar es **aviso, no urgencia** (el Yape del negocio también recibe pagos que no son de una venta). El **id de cada alerta es ESTABLE** —es lo que hace que «posponer» sirva— y se guarda **por usuario** en `tblAlertasVistas`. Lo que nombra personas (anulaciones, descuentos) pide `verTodo`. 🛡️ `lib/alertas.test.ts`.

### Pruebas de carga (emulador local, nunca producción)
- 🔑 **Toda prueba de volumen o concurrencia va contra el EMULADOR, jamás contra el proyecto real**: `firebase.json` → `emulators.firestore` (8080) y proyecto `demo-`, que no existe en la nube ⇒ `npx firebase emulators:start --only firestore --project demo-appadm`. ⚠️ **El script lleva candado** (aborta si `FIRESTORE_EMULATOR_HOST` no es local o el proyecto no empieza con `demo-`): escribe **miles** de documentos y un error de dedo contra producción sería destructivo.
- ⚠️ **Los tiempos del emulador NO son los de producción**: sirven para juzgar **corrección bajo concurrencia**, no latencias.
- 📌 **Medido (emulador, 2.000 SKU y 2-3 cajas)**: cada venta escribe **10 documentos**; stock **sin sobreventa** (las últimas unidades se venden entre muchos intentos y el resto recibe *"Stock insuficiente"*); **doble cobro del mismo pedido: 1 exitoso y 1 rechazado**; numeración **sin huecos ni duplicados**.
- 🔑 **Lo que la prueba confirmó como decisión de diseño**: **la serie por caja es lo que hace escalar**; con **una sola serie compartida**, 2 simultáneas ya tardan ~3,5 s y a las 16 empiezan los `ABORTED`.
- ⚠️ **Sesión única**: cada persona necesita **su cuenta** (el modal *Sesión en otro dispositivo* bloquea el cobro hasta *Continuar aquí*).
- 🔥 **ESTRÉS y 3 CAJAS (21/09/2026, emulador)**: la rampa aguanta **hasta 16 ventas simultáneas sin fallos** y **rompe a las 32**; en **ráfaga sostenida, 999 de 1.000 ventas en 130 s (7,7 ventas/s)**; y con **3 cajas, 3 series propias y 3 turnos: 72/72 cobros simultáneos y 360/360 ventas de jornada**, sin huecos, 0 stocks negativos y **los 3 turnos cuadran al céntimo** ⇒ **un turno por cajón es el modelo que cierra**. ⚠️ Los dos puntos flojos son de **contención, no de datos**: el **contador `pedido` compartido** pierde intentos desde **~36 pedidos simultáneos**, y **el mismo producto vendido por las 3 cajas a la vez** da `ABORTED: Transaction lock timeout` (**nunca hubo sobreventa**) ⇒ ✅ **hecho** (25/09/2026): ver `ejecutarTransaccion()` en la sección de Firestore. ⚠️ Los tiempos son del emulador: **a 1 venta cada 4-5 min por caja estamos ~1.000× por debajo del techo**.
- 📌 **El documento del TURNO tiene su propio techo (medido)**: guarda el array **`ventasDelTurno` completo y lo reescribe en cada venta** ⇒ **917 bytes por venta** y **~130 KB con 200 ventas**; el 1 MiB de Firestore llegaría a **~1.600 ventas en un mismo turno** ⇒ **partir el día en turnos (mañana/tarde)** antes que dejar un turno de 800+ ventas.

## Quality Requirements (MANDATORY)

All code changes and new features MUST follow these practices. No exceptions.

### Firestore
- Use `writeBatch` or `runTransaction` when updating multiple documents (never sequential `await` loops for related writes).
- Never use non-null assertions (`!`) on Firestore reads — always guard with `if (!x) return`.
- Never pass `undefined` as Firestore field value — use conditional spread: `...(val ? { field: val } : {})`.

### TypeScript
- No `any` types. Use proper types or `unknown` + narrowing.
- No non-null assertions (`!`) on optional fields — use `?? 0`, `?? ''`, or guard.
- Export types from services/hooks for reuse.

### React
- Extract reusable logic into custom hooks (`src/hooks/`) or utility modules (`src/lib/`).
- Deduplicate shared code (`fmt`, `estadoStock`, toast logic, etc.) into `src/lib/ui-utils.ts` or domain-specific utils.
- Components > 300 lines should be split into sub-components.
- Use `React.memo` for expensive list items if re-renders are frequent.

### Styling
- No hardcoded `bg-white` — use `bg-background` or `bg-card` for dark mode compatibility.
- Use `cn()` from `@/lib/utils` for conditional classes.
- Menu items with long labels: use `items-start` (not `items-center`) so icons align top when text wraps.
- Horizontal scroll containers: use `scrollbar-none` utility class.

### Error handling
- All async operations must have try/catch with user-facing error messages.
- `localStorage` writes must catch `QuotaExceededError`.
- Prefer `console.warn`/`console.error` over silent `catch {}`.

### Architecture
- Services (`src/services/`) handle Firestore logic — keep it out of components.
- Pages (`src/pages/`) handle UI only.
- Shared utilities go in `src/lib/`.
- Constants go in `src/constants/`.
