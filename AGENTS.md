# AGENTS.md — appadm-web

## What this is

React + TypeScript SPA (point-of-sale / inventory admin) backed by Firebase (Auth + Firestore). No router — navigation is state-driven in `src/App.tsx`. UI language is Spanish.

**Repos relacionados** (los versiona el usuario, **no** este agente): la app móvil **`AppAdm`** (Expo/React Native), el **backend `appadm-sunat`** (FastAPI + `sunat_py`, corre en `192.168.1.7:8000`) y el **puente de Yape `appadm-yape-puente`** (Android/Kotlin: escucha la notificación de Yape y escribe `tblPagosYape`). Un cambio puede tocar los cuatro: si un defecto se arregla acá y **el mismo defecto existe en la RN, se arregla también** y se avisa (no alcanza con arreglar el web).

## Invariantes y trampas (leer antes de tocar código)

Reglas que ya costaron un bug o que salieron de una decisión explícita del usuario. **No "arreglarlas" por iniciativa propia.**

### Caja y arqueo
- **El arqueo cuadra el efectivo, y nada más**: `efectivoEsperado = montoInicial + totalEfectivo − gastosEfectivo − vueltoTransferencia`. Las transferencias **no entran** (ni ahí, ni en `totalNeto = totalVentas − totalGastos`, ni en la diferencia): cambiar `totalTransferencia` **no puede** mover el esperado, el contado ni la diferencia — en el arqueo es **informativa**. 🔑 **Esa fórmula vive en UN solo lugar: `efectivoEsperadoDe()` (`lib/arqueo.ts`)** — estaba escrita a mano en **6** sitios y **dos** sin restar `vueltoTransferencia` (el modal de cierre y `analizarCierre`), así que el cajero comparaba contra otro número. **No volver a escribirla a mano** (la usan `turnos.ts` ×2, `reportes.ts`, `egresos.ts`, `compras.ts`, `CierreCaja.tsx` y `auditoria-caja.ts`). Verificado: **92/92 turnos cerrados** dan idéntico al guardado.
- ⚠️ **El consolidado "Caja del día" suma SOLO turnos cerrados.** Un turno abierto tiene esperado pero **todavía no tiene contado**, así que incluirlo inventa una diferencia. Ahora `montoInicialTotal` / `efectivoEsperadoTotal` / `efectivoContadoTotal` se acumulan solo si `estado === 'cerrado'`, y el rótulo avisa cuántos quedaron abiertos.
- **`tipo` = bolsillo, `medio` = detalle.** Se guarda `{ tipo: 'efectivo' | 'transferencia', medio: 'efectivo' | 'yape' | 'plin' | 'transferencia' | 'tarjeta', monto, operacion? }`. `tipo` es lo que ya entienden el arqueo, los reportes, las anulaciones, el cobro y la RN: **poner `tipo: 'yape'` rompe ~8 lugares en silencio**.
- ⚠️ **`bolsilloDe()` devuelve `'credito'` para `'credito'`, `'mixto'` y cualquier valor desconocido** — **nunca cae a efectivo**. Un medio desconocido que cayera a efectivo **infla el cajón** y produce un faltante fantasma (fue un bug real, ver bloque ·10). Reparto de una venta: **`bolsillosDeVenta()`** (`lib/pagos.ts`) como **regla única**, usada por el alta **y** la anulación.
- **Una venta a crédito no entra a ningún bolsillo** (queda por cobrar); **un cobro de crédito sí**, en el bolsillo del medio con que se cobró.
- **Cada bolsillo tiene dos ejes**: el **total** (plata que entró al cajón/banco: contra eso se concilia) y el **origen** (`lib/arqueo.ts`: ventas del día / cobranza de crédito / notas). Ahí `ventas` es el **residuo** — las partes siempre suman el total guardado, y `consistente: false` avisa si lo derivado no lo explica.
- **Conciliación por billetera (`mediosDelTurno`, `lib/arqueo.ts`)** = lo que el sistema dice que entró por Yape/Plin/tarjeta, para cruzarlo contra la app/banco. Se declara al cerrar (**opcional**, se guarda como `conciliacion` en el turno y en `tblCierresCaja`) y se muestra en el arqueo y en el PDF del cierre. ⚠️ **El `medio` fino existe desde el 16/09/2026**: antes todo cae en **"Transferencia (sin detalle)"** — no inventar un medio (una **NC** también cae ahí: `notas.ts` guarda el bolsillo del original). Verificado: **49/49** turnos con medios cuadran con el `totalTransferencia`.
- **Conteo ciego** (`config.conteoCiego`, Configuración → Empresa, **apagado por defecto**): al cerrar, el cajero escribe el conteo **sin ver** el "Debería haber"; la diferencia aparece recién en el paso de análisis. Es el control que evita que alguien "cuadre" copiando el esperado.
- **Los documentos de caja van identificados y firmados**: `abrirPDFArqueo`/`abrirPDFCierreCaja` reciben `empresa` (`EmpresaPDF`: nombre, RUC, dirección) e imprimen **dos líneas de firma** (cajero —con quién cerró el turno— y supervisor). ⚠️ Si se agrega un PDF de caja nuevo, **pasarle la empresa y las firmas** (ya están en Configuración → Empresa).
- **`tblTurnos` es registro de caja: no se reescribe.** Para corregir un turno histórico se pide permiso, se toca **solo** el campo necesario (el turno **y** su doc de `tblCierresCaja`), se deja `observaciones` y se registra en `tblAuditLog`.
- ⚠️ **Las fechas de los items del turno se guardan en UTC**; las de turno/reportes son locales. Un cobro de las 21:43 del 14 figura como **15/09 02:43Z**: un turno del 14 puede tener items "del 15" sin que nada esté mal.
- El cajero opera con **su** turno, salvo `verTodo` (supervisor). No se emite comprobante **ni se cobra crédito** con el turno cerrado.

### Fiscal (SUNAT)
- **`Producto.precio` es precio FINAL al público (con IGV incluido)**: no se recarga el 18% al cobrar ni se guarda el precio sin IGV.
- **El comprobante declara lo que se COBRA**: `lib/sunat-importes.ts` reparte el descuento por línea **antes** de despejar el IGV. Al revés, el descuento se aplicaría sobre una base que ya no es la cobrada.
- 🔑 **La BOLETA CONSOLIDADA (consolidación de las NV del día) tiene que declarar el descuento de las NV que agrupa**: `generarConsolidado` (`services/consolidado.ts`) suma los totales (ya netos) y arma las líneas con los items de cada NV **a precio de lista**, así que el descuento va **declarado aparte** (`descuentoTotal` + `descuento_total` = Σ `descuentoDeVenta(nv.venta)`). 📌 **Bug del 18/09/2026**: el consolidador **tiraba el descuento** (y unía items por `id` sin mirar el precio) → líneas a precio de lista, **total menor** y **sin fila de descuento**; como el XML suma `Σ líneas`, SUNAT habría recibido **más de lo cobrado**. Las reglas viven en **`lib/consolidado.ts`** (`consolidarItems` —clave **`id|precio|unidad`**—, `totalConsolidado`, `descuentoConsolidado`). ⚠️ **La RN tiene el mismo defecto** en `helper/ConsolidadoHelper.js`.
- **El IGV solo existe en afectación `'10'`**: `valorUnitarioSunat(precio, afectacion)` divide entre 1.18 **solo** para `'10'`; exonerado `'20'`, inafecto `'30'` y gratuitas van tal cual (dividirlas haría que el comprobante declare **menos** de lo cobrado).
- 🔑 **El receptor de la BOLETA CONSOLIDADA es configurable** (`config.clienteDefaultNombre` / `clienteDefaultDni`, en **Configuración → SUNAT → Boleta consolidada**; regla única: `nombreClienteConsolidado()` y `documentoClienteConsolidado()`, `lib/consolidado.ts`). La consolidada agrupa las NV del día: **no hay cliente real** ⇒ documento `00000000` y un **rótulo** que **se declara a SUNAT** (cambiarlo es decisión fiscal). ⚠️ **Un nombre vacío vuelve al valor por defecto** y no requiere migración.
- **Los items manuales del PDV** usan `config.tipoAfectacionManual` (default `'20'`) y **debe coincidir con el catálogo**: si no, el comprobante declara más (o menos) de lo cobrado.
- **El backend vive aparte** (`appadm-sunat`): un cambio ahí **no hace efecto hasta reiniciarlo**, y lo despliega el usuario. El SDK `sunat_py` es de PyPI y **no se toca**: el backend parchea el XML por `replace` antes de firmar.
- 🔑 **Todo lo que se manda a la API de SUNAT va con 2 DECIMALES** (`cantidad`, `precio_unitario` y los totales): el backend valida con Pydantic (`app/schemas/invoice.py`) y **rechaza el envío con *"decimal input should have no more that 2 decimal places"***. La regla vive en **`itemsParaSunat()`** (`lib/sunat-importes.ts`, puro y testeado): reparte el descuento y deja el precio unitario en 2 decimales **sin perder el total cobrado** (el residuo del redondeo se repone línea por línea, de la más flexible —cantidad 1— a la menos flexible, en pasos de `cantidad` céntimos); `cantidadSunat()` ajusta la cantidad (una venta por peso con 3 decimales se declara con 2); en las líneas **gravadas** el valor sin IGV (`precio / 1.18`) también se redondea; y **todos los totales** pasan por `redondear2()`. ⚠️ **El backend IGNORA el bloque `totales`**: arma el XML con `cantidad × precio_unitario` de cada línea (`app/services/invoice_service.py`), así que lo que manda es el **precio unitario por línea**. 📌 **Bug del 18/09/2026**: el web mandaba hasta **6** decimales (`DECIMALES_PRECIO`): una línea con descuento daba `1.09 / 2 = 0.545` y el envío se caía. ⚠️ **La RN tiene el mismo defecto** (`AppAdm/services/sunat.js`).
- 🔑 **Los correlativos tienen DOS espacios y viven en `tblContadores`**: `notaVenta_{serie}` para **notas de venta** y `sunat_{serie}` para boletas, facturas y NC/ND. La clave se arma **siempre** con **`claveContador(tipoDoc, serie)`** y el campo es **`CAMPO_CONTADOR` = `ultimoCorrelativo`** (ambos en `lib/contadores.ts`, puro y testeado); se **siembra desde el máximo ya emitido** cuando el contador no existe. ⚠️ **Regla que ya se rompió**: el flujo de ventas pendientes usaba `sunat_{serie}` y el campo `contador` → nació un contador paralelo **que arrancaba en 1** mientras las NV iban por `notaVenta_NV01 = 173` (habría **repetido un número ya emitido**). Nunca escribir la clave ni el campo a mano.

### Envío automático a SUNAT (web)
- 🔑 **Una regla (`lib/sunat-auto.ts`, puro y testeado) y un solo camino de envío**: `services/sunat-auto.ts` reclama y manda con `enviarDocumentoASunat`/`enviarNotaASunat` (los del botón manual); `use-sunat-auto.ts` (montado en el `Shell`) lo corre al abrir, cada `sunatAutoIntervaloMinutos` y al volver el internet. **Plazo único y configurable: 3 días** (`config.sunatAutoDiasVencimiento`), medido en **día local** (la factura vence a los 3 y la boleta a los 7 ⇒ se usa el más estricto).
- ⚠️ **Nunca se manda solo**: NV y pedidos, lo `aceptado`, lo `rechazado`, lo `anulado` ni **lo vencido**; el **botón manual manda todo eso** y sigue igual con el automático apagado (`respetarInterruptor: false` en «Enviar pendientes ahora»). Una nota **espera a que su comprobante esté `aceptado`** (fail-open si no lo encuentra).
- 🔑 **Reclamo transaccional** (`reclamarDocumentoSunat`): sin él **dos pestañas mandan el mismo comprobante**; un `enviando` colgado se recupera a los 5 min y un duplicado no daña (**1033** = aceptado). La consulta es **una igualdad sobre `sunat.estado`** (`pendiente`/`error`/`enviando`/**`rechazado`** ⇒ **sin índice compuesto**): `rechazado` está **solo para la alerta** (📌 sin él no se disparaba nunca).
- 🔑 **El interruptor se lee del SERVIDOR** (`getDocFromServer`: con la caché llega viejo y una pasada podía mandar **con el automático apagado**). Alertas: `sunat-pendiente` y `sunat-rechazado`. ⚠️ **Manda el NAVEGADOR**: solo cubre los días en que alguien abre el app y la página tiene que **alcanzar la API** (el CSP de `firebase.json` no permite una IP de la red local, y desde `https` un `http://…` sería contenido mixto).

### Pedidos (venta enviada a caja) y stock
- **Un pedido no es un comprobante**: `tipo: 'PENDIENTE'`, `serie: ''`, `numero: 0`, sin bloque `sunat`, sin forma de pago, y su código `PED-000123` sale del contador `pedido` (`CLAVE_PEDIDO` + `codigoPedido`, `lib/contadores.ts`). **La serie y el correlativo se asignan una sola vez, al cobrar** (`cobrarVentaPendiente`, con `claveContador(tipoFinal, serieDestino)`); eliminar un pedido **no deja huecos**. No volver a numerar en el alta.
- 🔑 **El pedido NO toca el stock: el inventario se descuenta recién al cobrar, en UN solo lugar** (`cobrarVentaPendiente`). Decisión explícita del usuario (17/09): *"un pedido es un ticket en espera, no una reserva"*. Antes reservaba stock con movimientos `venta_pendiente` y había que reponerlos al eliminar; eso creaba **dos caminos de escritura de stock** (alta y cobro) y dejaba stock retenido si el pedido quedaba colgado. **No reintroducir la reserva sin hablarlo**: si algún día se quiere apartar producto (seña, cliente que vuelve), va como **capa explícita y visible** (campo `reservado` mostrado en el catálogo), no como descuento silencioso.
- **Eliminar un pedido = marcarlo `cancelado`** (`cancelarVentaPendiente`, con motivo obligatorio): **una sola escritura** — no lee ni escribe `tblProductos` ni crea movimientos, porque no hay nada que deshacer. Se registra en `tblAuditLog` (`accion: 'eliminar_venta_pendiente'`). ⚠️ **No es un borrado físico**: el documento queda en `tblDocumentos` con `estado: 'cancelado'`, el motivo y quién lo eliminó — sirve para rastrear por qué un pedido no llegó a comprobante. Desaparece de la lista de pendientes (`obtenerVentasPendientes` filtra `estado == 'pendiente'`) y **de todos los reportes** (filtran `tipoDoc` contra `NV/BOLETA/FACTURA/NC/ND`).
- **Los pedidos los ve el cajero en el PDV**, no en una pantalla aparte: `PanelVentasPendientes` se monta arriba del carrito y solo si tiene `verVentasPendientes`. ⚠️ **La lista NUNCA debe depender de la caja para mostrarse**: `obtenerVentasPendientes()` trae **todos** los pendientes y el reparto lo decide **`repartirPedidos()`** (`lib/pedidos.ts`), no la consulta. Filtrar en Firestore (o esconder el panel cuando no hay caja) fue el bug real del 17/09: los cajeros no tenían caja y el pedido `PED-000001` era **imposible de cobrar**. Un pedido que no se ve es una venta perdida: **ante la duda, mostrar**.
- ⚠️ **El cobro de un pedido usa las series de la caja del CAJERO** (`serieBoleta`/`serieFactura`/`serie_prefijo` de `usePermisos()`, con la config de la empresa como respaldo) igual que el PDV: si no, un cajero de la caja 2 emitiría con la serie de la caja 1.
- **Cajas = puntos de emisión** (`services/cajas.ts`): nombre + **8 series** (Boleta, Factura, NV, NC, ND, NCB, NDB). Se crean en **Configuración → Cajas** y se asignan al usuario en **Usuarios → Editar → Caja**. ⚠️ **Quien la necesita es el CAJERO** (es quien emite: define con qué serie sale el comprobante); el **vendedor no** — su caja solo **dirige** el pedido. Si un usuario no tiene caja, se usan las series de la configuración de la empresa (funciona, pero deja de ser explícito).
- 🔑 **Caída de una caja con pedidos abiertos (decisión del usuario, 17/09)**: el `cajaId` de un pedido es **de ruteo** y **nadie más lo lee** (las series las pone la caja que **cobra**), así que conviven dos mecanismos: **(A) transferir** los pedidos abiertos (**Configuración → Cajas → Transferir pedidos**, `moverPedidosDeCaja()`: `writeBatch` + `tblAuditLog`) y **(B) rescate**: el panel muestra los de **otra** caja aparte y los deja cobrar con confirmación (*"se va a emitir con la serie de tu caja"*). Con (A) queda el orden; con (B) no se pierde una venta. El reparto es **`repartirPedidos()`** (`lib/pedidos.ts`, puro y testeado): sin caja se ve todo, con caja los propios + los sin caja, y los ajenos van a `otrasCajas` (nunca se ocultan). El documento cobrado queda con **la caja que lo emitió**.
- 🔑 **Modo pedido: el cobro ocurre en el CARRITO, no en la tarjeta** (decisión del usuario, 17/09). `Cobrar pedido` llama a `onCobrarPedido` y el PDV guarda `pedidoActivo` (`lib/pedidos.ts` → `pedidoParaCarrito()`): el carrito muestra **sus** items en solo lectura (franja ámbar) y el cajero elige **comprobante + forma de pago** con la UI de abajo; el botón pasa a **`Cobrar pedido S/ …`** → `cobrarVentaPendiente`. 🔑 **`total` es el del pedido cuando hay pedido activo** (`const total = pedidoActivo ? pedidoActivo.total : totalCarrito`), así el resumen de pagos y las validaciones no pueden contradecirse: **es el monto COTIZADO por el vendedor y no se recalcula** con las promos del día. En modo pedido se ocultan **envío, descuentos, cliente, crédito** y las acciones del carrito. ⚠️ **No volver a poner un cobro embebido en la tarjeta**: tenía su propia copia de comprobante, formas de pago y validaciones — dos lugares y dos reglas para lo mismo.
- 🔑 **El crédito se maneja directamente en caja (decisión del usuario, 17/09)**: un pedido del vendedor se cobra **siempre al contado** y por eso **en modo pedido no se ofrece "Crédito"**. Si el cliente quiere fiado, el **cajero** arma la venta como cualquier otra y la cobra a crédito con la validación de saldo (`lib/credito.ts`). El vendedor tampoco elige forma de pago al enviar, así que **un pedido nunca nace con intención de crédito**. ⚠️ Si algún día se quisiera permitir, hay que resolver antes qué pasa con el saldo: `calcularSaldoCredito` lee `venta.tipoPago === 'credito'` y `cobrado`, y `cobrarVentaPendiente` no escribe `cobrado`.
- **Al cobrar, si el stock ya no alcanza, el cobro falla con un mensaje claro** (*"El stock de X se agotó mientras el pedido esperaba en caja"*): es el costo de no reservar y el cajero tiene que enterarse **antes** de cobrar, no después con el inventario mintiendo.
- **Dos personas en una venta = una regla, `lib/personal.ts`** (`personalDeVenta`, `lineasPersonal`, `textoPersonal`): **con vendedor y cajero distintos salen los dos; si trabajó una sola persona, sale una sola vez**. Se usan `venta.vendedor` (quien armó el pedido) y `venta.cajero` (quien cobró), con `doc.vendedorNombre`/`doc.cajero` de respaldo. ⚠️ `registrarVenta` escribe el **mismo usuario** en `cajero` y `vendedorNombre`, así que la regla **colapsa el nombre repetido** (si no, el ticket lo diría dos veces). ⚠️ **`venta.cajero` de un pedido NO es el vendedor** (era el bug: al mandar a caja se escribía el vendedor y el comprobante lo imprimía como si hubiera cobrado él); al cobrar se guardan los dos y se imprime (`Vendedor: Ana · Cajero: Luis`), y en el arqueo por comprobante como `· Vend: Ana` (solo si no es el cajero del turno).
- ⚠️ **Los movimientos de stock siguen el formato del kardex** (`services/kardex.ts`): `tipoMovimiento`, `cantidad` **positiva** y el signo lo decide `esEntrada()`; además `stockAnterior`/`stockNuevo`/`fecha`. Un `tipo` suelto o una `cantidad` negativa no se leen (quedan invisibles en el kardex). El cobro de un pedido escribe un movimiento `venta` igual que `registrarVenta` (con `vecesVendido: increment(1)`).
- 🔑 **Un pedido tiene que declarar el DESCUENTO igual que una venta directa**: `crearVentaPendiente` guarda **`descuentoTotal`** (camelCase: el que leen `lib/pdf.ts` y `lib/sunat.ts`) **y** `descuento_total` (nombre viejo). 📌 **Bug del 18/09/2026**: el pedido guardaba **solo** `descuento_total`, así que al cobrarlo el comprobante **no veía descuento**: sumaba las líneas a **precio de lista** y declaraba el total ya descontado **sin ninguna fila de descuento** que lo explicara — y el XML habría declarado más. **La lectura es una sola regla: `descuentoDeVenta(venta)`** (`lib/sunat-importes.ts`, pura y testeada: camelCase con respaldo en snake_case) y la usan el PDF, el XML de SUNAT y el carrito del cajero (`pedidoParaCarrito().descuento`, mostrado en la franja ámbar del modo pedido). ⚠️ Los **precios de las líneas siguen siendo los de lista**: lo que se declara es el total con la fila `Descuento` (modelo SUNAT), no un precio unitario ya rebajado.
- 🔁 **Un pedido idéntico no se crea dos veces**: si el mismo vendedor manda la misma venta y ese pedido **sigue pendiente dentro de los 15 minutos** (`VENTANA_DUPLICADO_MINUTOS`), `crearVentaPendiente` **rechaza el alta** y devuelve el código del que ya existe (`{ duplicado: true, codigoPedido }`); el PDV entonces pide confirmación (*"¿Enviar otro igual?"*) para el caso legítimo —otra venta con los mismos productos—, y con `permitirDuplicado: true` el documento queda marcado `duplicadoConfirmado: true`. 📌 **Caso real (18/09/2026)**: un reenvío creaba dos pedidos; el cajero cobraba uno y el otro quedaba colgado **para siempre** en su lista. Las reglas viven en **`lib/pedidos.ts`** (`huellaPedido()`: vendedor + total + líneas ordenadas, **sin fecha** —para reconocer el reenvío— y sin cliente; y `pedidoDuplicado()`, que también recalcula la huella de los pedidos viejos que no la tienen guardada), puras y testeadas. ⚠️ La comprobación es **fail-open a propósito**: si la consulta de pendientes falla, el pedido se crea igual — es una ayuda contra el error humano, no un candado que pueda bloquear una venta.

### Inventario valorizado (costo promedio ponderado)
- 🔑 **El costo con el que se valoriza el stock es UNO solo: `costoDeProducto()` (`lib/valorizacion.ts`)** — el **promedio ponderado móvil** (`producto.costoPromedio`, guardado con **4 decimales**) y, mientras el producto no tenga uno, el **último costo** (`ultimoCostoDeProducto()`: `precioCompra` y, si está vacío o en **0**, el campo viejo `costo`) **como respaldo**. Lo usan el kardex (columnas *Costo unit.* y *Valor*), el reporte **Valorización** de Inventario, los **reportes de inventario** (`lib/inventario-reportes.ts`: stock general, mayor inversión, por categoría, general y utilidad), el **margen** de `services/analisis.ts` y el aviso **BAJO COSTO** del PDV. **No volver a escribir `stock × precioCompra` ni leer `precioCompra` a mano para plata.**
- 📌 **Bug del 19/09/2026 (el costo partido en dos)**: Análisis y los reportes leían `precioCompra` y **ninguna compra escribía ese campo** ⇒ **dos costos del mismo producto en dos pantallas** (8 de 36 desactualizados), y el equivocado era el que se mira para poner precios. **`registrarCompra` escribe `precioCompra` = costo por unidad base** (un ítem con costo 0 **no** lo pisa) y lo registra en `tblHistorialPrecios`. Detalle: historial ·41.
- ⚠️ **Un producto con stock y sin ningún costo vale S/ 0** en la valorización **y da 100% de margen** en el reporte de utilidad: no se distingue «no hay dato» de «costo cero». Limitación conocida (el Inventario avisa *"N sin costo (valen S/ 0)"* y el Excel lo rotula *Sin costo (vale 0)*), **fijada por un test**.
- 🔑 **Entrada vs salida (la regla del método)**: una **entrada con costo** (compra) mueve el promedio —`(stockAntes × promedio + cantidad × costo) ÷ stockFinal`—; una **salida** (venta, ajuste negativo) se valoriza **al promedio vigente y NO lo mueve** —la mercadería que sale no arrastra el precio de la última compra, que es la gracia del PPP—; una **entrada SIN costo** (devolución, anulación, ajuste positivo, que no piden costo) se valoriza **al promedio vigente** y tampoco lo mueve: **tratar el costo faltante como 0 hundiría el promedio** y valorizaría el inventario de menos; y con **stock previo ≤ 0** el promedio pasa a ser el costo de la entrada (no hay nada que ponderar y dividir por un stock negativo no tiene sentido).
- 📌 **El promedio se guarda con 4 decimales** (`DECIMALES_COSTO`) y los **valores** con 2: redondear el promedio en cada paso **acumula error**. ⚠️ **La valorización se escribe en los 7 caminos que tocan stock** (compra `compras.ts`, nota de crédito, venta `registrarVenta`, anulación de NV, cobro de pedido `cobrarVentaPendiente`, ajuste y toma física de `Inventario.tsx`) llamando a **`valorizacionDeMovimiento()`** (`services/kardex.ts`): **un camino nuevo de stock que no la llame deja el kardex sin costo y el promedio viejo**. El cobro de un pedido lee el `costoPrevio` de cada producto **dentro de la transacción** (no está en el carrito).
- ⚠️ **Los movimientos anteriores a la función no tienen valorización y muestran `s/d`** — no se inventa un costo que nunca se registró: los productos sin una entrada desde entonces se valorizan con el último costo (la columna **Origen del costo** del Excel y el contador **"N con último costo"** del Inventario lo dicen). El respaldo y sembrar el promedio dan lo mismo ⇒ **no hace falta migración**.

### PDV: el catálogo se dibuja por páginas
- 🔑 **El catálogo del PDV NO se pinta entero: se dibuja de a `PAGE_CATALOGO` (60) tarjetas** (`Pdv.tsx`: `visibles` + `paginados = lista.slice(0, visibles)`, `InfiniteScroll` + *Ver más* + *«Mostrando X de Y»*). No cambiar la suscripción por un `limit()`: rompería la búsqueda y el stock en vivo.
- ⚠️ **El reset de la página va en el EVENTO, no en un efecto** (el `onChange` del buscador y los chips hacen `setVisibles(PAGE_CATALOGO)`): sincronizarlo con un `useEffect` sube el baseline de lint.
- 📌 **Medido el 21/09/2026 (build de producción, 2.000 productos)**: el catálogo llega en **6,2-6,6 s** y el heap baja a **11-29 MB** (antes 41-43 MB). En el build de **desarrollo** los números son ~2× peores ⇒ **medir siempre contra el build de producción**.

### Afectación (IGV) — leer antes de tocar cualquier flujo de venta
- 🔑 **La afectación es de CADA PRODUCTO** (`Producto.tipoAfectacion`): manda por encima de cualquier configuración. `afectacionDe(item, { regionExonerada })` (`lib/sunat-importes.ts`, puro y testeado) es la **regla única**: si el item trae la suya, esa; si no, el default del negocio (`config.regionExonerada ? '20' : '10'`). **`config.regionExonerada` NO es un override** — es solo el default de lo que no trae dato (antes era **decorativa**: se mostraba en Configuración y no se usaba en ningún cálculo).
- 🔑 **Los items de un DOCUMENTO llevan otra forma que los del carrito**: el carrito usa `quantity` + `precioVenta` por presentación; el documento usa `cantidad`/`cantidadEnUnidadBase` en **unidades base**, `precioVenta` por **unidad base**, `subtotal`, `unidad`, `categoria` y **`tipoAfectacion`**. 📌 **El bug del 18/09/2026**: `enviarACaja` (pedido) mandaba el formato del carrito, así que los pedidos se guardaban **sin `tipoAfectacion`** → al cobrarlos, `it.tipoAfectacion || '10'` los declaraba **GRAVADOS** y un producto exonerado (`'20'`) salía con **Op. Gravadas + I.G.V. 18%** en el comprobante. Con una venta por presentación (factor > 1) el `subtotal` además habría salido inflado por el factor. **Al agregar un flujo nuevo de venta, copiar el formato de `registrarVenta`**, no el del carrito.
- **Los items de "Embalaje y Otros"** (sin producto en el catálogo) llevan su **propia `afectacion`**: arranca con `config.tipoAfectacionManual` y el cajero la cambia por item con el selector del carrito (catálogo `TIPO_AFECTACION`). Viaja igual en la venta directa y en el pedido; `VentaPausada` la guarda para no perderla al pausar/recuperar.
- **Revisar la afectación con los ojos en el PDF**: si un comprobante muestra filas *Op. Gravadas / I.G.V.*, hay al menos un item declarado `'10'`; en una región exonerada eso es un error, no criterio.

### Firestore
- **Igualdad + rango/orderBy ⇒ índice compuesto** declarado en `firestore.indexes.json` y desplegado con `npx firebase deploy --only firestore:indexes`. ⚠️ **Nunca `firebase deploy --force`** (borra índices que no estén declarados ahí).
- 🔑 **`undefined` NO es un valor válido: Firestore lo RECHAZA al escribir** (*"Function transaction.set() called with invalid data. Unsupported field value: undefined"*) y **TypeScript no avisa** (un campo opcional `string | undefined` compila perfecto). Fue un bug real: **enviar una venta a caja fallaba siempre** (`descuentoGlobalTipo: undefined`, `envio: undefined`). **Reglas**: (a) los opcionales que pueden faltar van con **spread condicional** (`...(x ? { campo: x } : {})`) o en **`null`** (`?? null`); (b) **en el borde de escritura**, envolver el payload en **`limpiarUndefined()`** (`lib/limpio.ts`, puro y testeado) — es la red de seguridad: borra los `undefined` en profundidad, descarta los sueltos dentro de arrays y **respeta `null`, `Date`, `Timestamp`, `deleteField()` e `increment()`** (son instancias de clase). Ya se usa en `ventas.ts` (alta, pedido, cobro, anulación), en `Inventario.tsx` y en **`services/sunat.ts`**: ahí el `updateDoc` del bloque `sunat` fallaba **aunque SUNAT ya hubiera aceptado el comprobante**, porque el CDR **no siempre trae** `cdr_code`/`cdr_desc`/`hash` (van por `datosCdr()` con `?? null`). Para diagnosticar antes de escribir: `rutaConUndefined(payload)`. 📌 **Caso real (28/09/2026)**: en **Egresos/Gastos**, con el proveedor escrito a mano no cargado, `proveedorId: undefined` hacía fallar **toda** la transacción (ni el gasto ni el total del turno se guardaban); ahora la pantalla manda `''`, el servicio limpia el payload (`services/egresos.ts`, 🛡️ `lib/egresos-escritura.test.ts`) y ese error se traduce con **`mensajeDeDatoInvalido()`**.
- `orderBy` **descarta** los documentos a los que les falta el campo: si puede faltar, ordenar en JS.
- **Borrados y actualizaciones masivas, por lotes** (`writeBatch`, 500) devolviendo **lo que realmente se hizo** (nunca 0 por un fallo parcial).
- Nunca `undefined` como valor de campo (spread condicional) ni `!` en lecturas.
- 🔑 **Toda transacción va por `ejecutarTransaccion()` (`services/transacciones.ts`), nunca por `runTransaction` del SDK**: el envoltorio **reintenta** la contención entre cajas (lock timeout, y el `failed-precondition` de *«stored version does not match»*) y, si igual falla, la cambia por *«El sistema está ocupado… Reintenta en un momento — no se registró nada»*. Qué es transitorio lo decide **`lib/reintentos.ts`** (puro y testeado), y ⚠️ **`failed-precondition` es ambiguo**: el de *«requires an index»* **no** se reintenta (bloque ·5). 🛡️ Dos tests-guarda fallan si un servicio usa `runTransaction` directo o si el envoltorio deja de traducir el error.
- **Diagnóstico contra producción**: **solo lectura** con la service account (`firebase-admin` instalado en una carpeta temporal **fuera** de los repos, y borrada al terminar). Los `uid` tienen 28 caracteres: no truncarlos.

### Sesión y sin conexión (offline)

### Avisos de pago de Yape
- 🔑 **Los avisos viven en `tblPagosYape` y los crea el PUENTE, no esta app.** El puente lee el aviso real de Yape (la notificación del celular del negocio). El POS **solo lee** y **avanza el estado**: `disponible → reservado → usado`, o `ignorado`/`anulado`. **La única excepción es el aviso de PRUEBA** (Configuración → Yape): prueba el circuito sin que alguien yapee, va con `origen: 'prueba'` —marcado en el PDV y en el cierre, con confirmación— y se borra de un toque (`borrarAvisosDePrueba`, que **nunca** toca un aviso real). 🛡️ `lib/yape-creacion.test.ts`. Un aviso real significa «el negocio recibió plata», no «alguien apretó un botón». El contrato del documento está en la cabecera de **`services/yape.ts`**; ⚠️ `fecha` tiene que ser un **Timestamp** (la query filtra por rango; un string se tolera al leer pero la query no lo encuentra).
- 🔑 **El ciclo de vida vive en `lib/yape.ts`** (puro y testeado: situación del aviso, lista visible, aplicación a la venta con su tope, resumen y cruce del turno) y **la transacción en `services/yape.ts`** (`reservarPagoYape` → `confirmarPagoYapeEnVenta` → `soltarPagoYape`, + `ignorarPagoYape` y `anularPagoYapeDeVenta`). **No agregar un segundo camino.** El **vencimiento es derivado** (no se guarda) y una **reserva vencida vuelve a estar disponible**: un navegador que se cierra a mitad del cobro no deja el aviso tomado.
- 🔑 **Por qué hay una RESERVA y no solo un candado al final**: el aviso se toma **antes** de cobrar. Si el único control fuera marcarlo `usado` tras guardar la venta, dos cajas aplicarían el mismo yape y la segunda se enteraría **después de haber cobrado**. La reserva es transaccional y **cross-caja**.
- ⚠️ **Un aviso dice un monto, NO una venta**: el monto que coincide con el total solo se **destaca** (ayuda visual, no una regla) y el cruce real es **al cerrar el turno**: `CierreCaja` (con `pagosYape`, que trae `Turnos.tsx` vía `obtenerPagosYapeDelTurno`) lista los avisos confirmados y **avisa si hubo cobros por Yape y ningún aviso**. ⚠️ Ese prop es `PagoYape[] | null` (**`null` = todavía no llegaron**, `[]` = llegaron y no hay ninguno). **No bloquea el cierre: informa.**
- 🔑 **Al confirmar se guarda el ID DEL DOCUMENTO, no `ventaId`**: `ventaId` es un id interno (`V-…`) que no sirve para encontrar la venta; el documento es `2026-9_BOLETA-B001-000001` (por eso `registrarVenta` devuelve **`documentoId`**). De eso depende que **anular la venta marque el aviso `anulado`** (la plata volvió al cliente), enganchado en `anularNotaVenta` y best-effort — **anular no puede fallar por esto**. ⚠️ **Una NC de una boleta NO está cubierta**.
- ⚠️ **Un estado que la app no entiende no se muestra ni se puede usar**: el panel lo dice (*«N aviso(s) con un estado que el sistema no reconoce»*).
- ⚠️ **`firestore.rules` NO se tocó, a propósito**: permite `read, write` a todo autenticado y basta que **una** regla permita, así que un bloque restrictivo para `tblPagosYape` sería **decorativo**. Endurecerlo exige ruleset por colección + cuenta dedicada del puente.
- 🔑 **Con varias cajas, el panel ayuda a no elegir a ciegas** (22/09/2026): la plata entra a **UNA** cuenta, el aviso **no dice de qué caja es** y todos ven la misma lista ⇒ cada aviso muestra **hora con segundos** + **«hace N s»** + pagador + N° de operación; se **avisa** si hay dos del mismo monto (`avisosDelMismoMonto`) y uno que no coincide con el total **pide confirmación** (`confirmarAntesDeAplicar`) — ⚠️ **no es un candado**: el control real es el **cruce del cierre**. Muestra el **`codigoSeguridad`** (lo único que distingue dos avisos del mismo monto: ⚠️ **no es identidad** ni prueba, puede repetirse) y **es la referencia del pago**, rotulada **`Ref:`** en ticket, A4, arqueo y turnos. 🛡️ `lib/referencia-pago.test.ts`.
- 🔑 **Los avisos anteriores se ven en `Reportes → Yape`** (22/09/2026): el panel del PDV lee **solo los del día** y los confirmados de un turno **solo al cerrarlo**, así que al día siguiente un yapeo era **invisible desde la app**. El historial lee **un rango de fechas** (una sola consulta de un campo ⇒ **sin índice compuesto**) y muestra la **situación derivada** de cada aviso, quién lo usó y en qué comprobante, los **sin usar** y los de **PRUEBA** —marcados, y **no suman**—; el filtro por situación y el buscador van **en memoria** (`filtrarAvisosYape`). 🛡️ Guarda: `lib/yape-historial.test.ts`.
- 🔑 **El latido del puente se ve en el PDV y en Configuración → Yape** (22/09/2026): el celular escribe `tblPuenteYape/estado` **cada 5 min** (y con cada aviso) y el web lo lee **en vivo**. **Por qué**: un panel vacío significa «no yapeó nadie» **solo si el puente late**; con el puente caído el panel también está vacío pero **la plata entró**. La regla es única, `estadoDelPuente` (`lib/puente.ts`): **activo** < 12 min, **demorado** 12-30, **caído** ≥ 30 (dos ciclos de gracia) y **`sin-datos` NO es «caído»** (nunca escribió). ⚠️ **Vive en la pantalla del PDV, no dentro del panel de avisos** (el panel se oculta cuando no hay avisos, que es justo el caso que importa). ⚠️ **No recupera** lo que el celular nunca leyó ni reemplaza el **cruce del cierre**. 🛡️ `lib/puente.test.ts`.

## Quality Requirements (MANDATORY)

All code changes and new features MUST follow these practices. No exceptions.

### Firestore
- Use `writeBatch` or `runTransaction` when updating multiple documents (never sequential `await` loops for related writes).
- Never use non-null assertions (`!`) on Firestore reads — always guard with `if (!x) return`.
- Never pass `undefined` as Firestore field value — use conditional spread: `...(val ? { field: val } : {})`.

### TypeScript
- No `any` types. Use proper types or `unknown` + narrowing.
- No non-null assertions (`!`) on optional fields — use `?? 0`, `?? ''`, or guard.
- Export types from services/hooks for reuse.

### React
- Extract reusable logic into custom hooks (`src/hooks/`) or utility modules (`src/lib/`).
- Deduplicate shared code (`fmt`, `estadoStock`, toast logic, etc.) into `src/lib/ui-utils.ts` or domain-specific utils.
- Components > 300 lines should be split into sub-components.
- Use `React.memo` for expensive list items if re-renders are frequent.

### Styling
- No hardcoded `bg-white` — use `bg-background` or `bg-card` for dark mode compatibility.
- Use `cn()` from `@/lib/utils` for conditional classes.
- Menu items with long labels: use `items-start` (not `items-center`) so icons align top when text wraps.
- Horizontal scroll containers: use `scrollbar-none` utility class.

### Error handling
- All async operations must have try/catch with user-facing error messages.
- `localStorage` writes must catch `QuotaExceededError`.
- Prefer `console.warn`/`console.error` over silent `catch {}`.

### Architecture
- Services (`src/services/`) handle Firestore logic — keep it out of components.
- Pages (`src/pages/`) handle UI only.
- Shared utilities go in `src/lib/`.
- Constants go in `src/constants/`.
